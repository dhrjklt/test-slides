Key facts

  • 2×RTX PRO 6000 Blackwell, 96 GB each, plus the older RTX 3090 for small models.
  • 2 copiesIdentical copies of the 27B model; LiteLLM sends each request to the less busy card.
  • FP8Half the memory of 16-bit, with near-identical answers.
  • 0 sDowntime: upgrade one card at a time while the other keeps serving.

Precision. Precision is how many bits store each number in the model — like choosing double, float or half in analysis code. FP8 uses 8 bits instead of 16, so the weights take half the memory; answers are near-identical.

KV cache. The KV cache is the model’s working memory of a conversation — like caching intermediate reconstruction results instead of rerunning the whole chain.

Embedder and reranker. They read their input once and return one result — like single-pass feature extraction — so they need almost no working memory.

04 · Serving 20 users

KEK S&C · October 2026

Serving 20 users on two GPUs

The bottleneck is GPU memory, not compute. Every active conversation needs working memory, called the KV cache.

GPU memory · 96 GB per card · illustrative split
model weights KV cache
working memory in 16-bit FP8 → ≈2× context
What users would feel What vLLM does Result
Long waits when many use it at once PagedAttention: memory handed out in small pages as each conversation grows Many more users served at once
Long documents fill the memory FP8 KV cache: working memory stored as 8-bit instead of 16-bit numbers About twice the context fits
Same instructions processed every time Prefix caching: shared opening text processed once and reused Follow-up answers start sooner
One big upload freezes everyone Chunked prefill: long inputs read in slices between other users’ work Answers keep streaming
GPU idle while writing word by word Continuous batching: new requests join the running batch at every step More total throughput

KV cache working memory for one conversation · vLLM the model server · capacity target ≈ 20 concurrent users; load test in progress.

Speed. Generating text is limited by memory bandwidth, not arithmetic — like a DAQ limited by readout rather than front-end speed. That is why batching and cache tricks matter more than raw FLOPs.
