Key facts

The gateway is LiteLLM: it gives every user one OpenAI-compatible API and a key. One Kubernetes Deployment today: a 27B copy on one RTX PRO 6000, with its own Service. Two copies, not one split model: independent copies give the highest throughput and redundancy. Splitting across both cards only pays off for very long contexts or a model too big for one card — and there is no NVLink between these cards.

The technical version of slide 04, as deployed (k3s/orchestrator.yaml). Offline, the gbasf2 corpus is chunked, embedded into pgvector and indexed with Postgres full-text search.

At query time: 6 dense + 6 keyword hits are fused with reciprocal-rank fusion, the Qwen3 reranker scores them and the best 3 go to the LLM. If the top score is below 0.9, the LLM rewrites the query once, retrieval runs again, the retry is re-scored against the original question, and the better attempt wins. The answer is generated from those chunks only, with [n] citations; if they do not fully cover the question, the model says what is missing.

Guardrail L2 would abstain outright when the top score is below 0.05 — skipping the rewrite and the LLM call. It is off in the deployment: GUARD_ENABLED=0, because the gates were calibrated on bge-reranker-v2-m3 and the pod now runs Qwen3-Reranker-0.6B.

  • native FP8 / FP4 · ECC memory · data-centre drivers for 24/7 service

Embedder and reranker — one-pass jobs that need almost no KV cache. Kept on their own card so chat is never slowed by retrieval work.

Precision — bits per number

FormatBits27B weightsQuality
BF16 / FP1616~54 GBreference
FP88~27 GBnear-identical — we serve this
FP44~14 GBsmall loss — test first

Weights and working memory (KV cache) both run FP8 — roughly doubling the memory left for users on each card.

Generating words is limited by how fast the GPU reads the weights — like a DAQ limited by readout bandwidth, not by the front-end.

Precision is how many bits store each number — like choosing double, float or half in analysis code. FP8 halves the weight memory at near-identical answer quality; we verify on our own question sets before moving to anything lower.

B6 · Backup · the KV cache

55th B2GM · KEK

How the KV cache works

The model's working memory: what it has already worked out about earlier tokens, stored so it is never recomputed.

One conversation

1 · Prefill — the whole prompt is read at once

2 · Decode — the answer is written one token at a time

Every token's keys and values are computed once and kept. Each new token only computes its own — and reads the rest from the cache.

prompt, cachedanswer, cached
One 96 GB GPU
model weights
~27 GB · FP8
weightsKV cache — shared by every open conversation

The space left after the weights decides how many people can be served at once — and how long their conversations can be.

PagedAttentionmemory in small blocks, taken only as a conversation grows
FP8 KV cachehalf the memory per conversation
Prefix cachinga shared start is computed once and reused

A transformer writes one token at a time, and each new token's attention looks at every earlier token. For each token and layer the model computes a key (what the token is about) and a value (what it passes on). Earlier tokens never change, so their keys and values are computed once and stored: that store is the KV cache.

Prefill reads the whole prompt in one go and fills the cache — compute-heavy, it is the pause before the first word. Decode adds one entry per token — memory-bandwidth-heavy, which is why bandwidth limits answer speed.

On a 96 GB card the 27B model takes about 27 GB in FP8; most of the rest is KV cache shared by all open conversations. vLLM stretches it with PagedAttention (small blocks), an FP8 KV cache (half the memory) and prefix caching (shared starts computed once).

B7 · Backup · follow-up questions

Follow-up questions reuse the cache

The chat API is stateless: every follow-up sends the whole conversation again.

Turn 1
system promptquestion 1answer 1
cached on GPU A
Turn 2
system promptquestion 1answer 1question 2
reused · new — read now

Only the new question is read → the answer starts sooner, even in a long conversation.

When it misses — the whole conversation is read again
1

Sent to the other GPU

The cache lives on the card that served turn 1 — so with two copies, the gateway must keep a conversation on the same GPU.

2

Evicted under load

On a busy card, the least-recently-used blocks are reclaimed for new requests.

3

Something earlier changed

A timestamp in the system prompt, or rewritten history, breaks reuse from that point on.

For us: today there is one copy, so follow-ups hit the cache. With the second copy, the gateway needs sticky routing — and system prompts must stay identical across requests.

The model does not remember a conversation between requests: Open WebUI or the agent resends everything — system prompt, earlier questions, answers and tool results — plus the new question. The start of each follow-up is therefore identical to the previous turn.

With prefix caching, vLLM keeps finished conversations' blocks until the space is needed, matches the new prompt block by block, and only prefills the new question. It misses when the follow-up lands on the other GPU, when the blocks were evicted under load, or when something earlier in the prompt changed.

For us: one copy today, so follow-ups reuse the cache; with two copies LiteLLM needs session affinity. Keep system prompts free of timestamps and per-request IDs so they are cached once and shared by everyone. Prefix caching is on by default in recent vLLM — worth confirming in our deployment.

Where the agent goes next. Today b2-computing-agent is a LangGraph ReAct agent: excellent for a question that needs a few tool calls, but we design the flow ourselves and the context fills up on long investigations.

Deep Agents is LangChain's harness on top of LangGraph: a built-in to-do planning tool, a filesystem the agent uses as working memory so large tool outputs stay out of the context, sub-agents that run in their own context (also in the background), and human approval through LangGraph interrupts. Because the result is still a LangGraph graph, our sub-agents, MCP servers and Langfuse tracing carry over.

OpenClaw and Hermes Agent are the popular personal-assistant agents of 2026: both run on your own hardware with persistent memory, and Hermes writes its own reusable skills. They are aimed at one person's machine and chat apps — OpenClaw in particular is widely flagged for its broad system access — so for shared Belle II operations Deep Agents is the better fit — and LangChain now integrates it with NVIDIA OpenShell, a sandboxed runtime with policy-based guardrails, so the long-running agent never touches the host directly. This is a plan under evaluation, not a decision yet.

Models and methods we are exploring

Guiding principle: better answers without adding operational effort.

planned

Decision models

A new kind of small model that gives a structured answer — yes / no, a probability or a ranking — instead of free text.

Use cases for us
  • route a question to the right sub-agent
  • check a tool call is safe before it runs
  • decide whether retrieved docs are good enough
  • check a long-running task is really finished
tried · parked

RAFT

Retrieval-augmented fine-tuning: fine-tune the model on questions together with retrieved documents, so it learns to answer from them.

Our experience
  • results were good
  • but every newer model means fine-tuning again
  • that is ongoing effort we want to avoid — plain RAG keeps updates to a re-index
testing

GraphRAG

Build a graph of entities and their relations from the documents, then retrieve from the graph as well as from text passages.

Why
  • better data extraction across many pages
  • answers that connect facts from different documents
  • testing whether it improves our results

Decision models are a new category of small models for agent pipelines (appearing from September 2026): instead of free text they return a bounded, structured answer — yes/no, a probability or a ranking. They fit the decision points we already have: routing to a sub-agent, checking that a tool call is read-only and safe, our RAG relevance gate, and checking that a long-running task is complete. We plan to explore them; check the current model options before naming any specific one.

RAFT — retrieval-augmented fine-tuning — trains the model on questions together with retrieved documents (including irrelevant ones), so it learns to use the context. We tried it and the results were good, but each newer base model means fine-tuning again. Our approach is to keep operational effort low, so retrieval without fine-tuning stays the default.

GraphRAG builds a knowledge graph of entities and relations from the docs and retrieves over it, which helps when an answer needs facts spread across many pages. We are testing it as a new approach for data extraction.

The travel agent is the answer to "why should a physics lab run LLMs": it is a second deployment of the same codebase, with a single tool — query_docs, the docs search from slide 04 — over the KEK travel rules instead of gbasf2.

It came from a proposal by Matsuoka-san and is used for Belle II secretarial tasks. Answers are scoped to the asker's role: the chat sends the user's audience with each question and retrieval only searches the rules that apply to them.
